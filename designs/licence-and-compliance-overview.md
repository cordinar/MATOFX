# Licence + compliance attestation — how it actually works

**Status:** describes the system as built on 2026-08-12 (ADR-0019, all seven slices, the anchoring rework, and the issuing + ledger-custody tooling).
**Companions:** [`licence-and-compliance-explained.md`](licence-and-compliance-explained.md) (the same subsystem in plain English, with analogies — for a prospect's evaluator, a customer's security reviewer, or a new maintainer) · `decisions/0019-licence-and-compliance-attestation.md` (the decisions and why) · `ARCHITECTURE.md` §16.47–16.65 (what each piece does) · [`funis-vendor-runbook.md`](funis-vendor-runbook.md) (what Funis actually does, step by step) · `designs/examples/` (real signed artefacts) · `matofx/src/matofx/docs/admin/15-your-licence.md` and `125-licence-compliance.md` (the customer-facing story).

This document is the plain-English orientation: what the system does, what depends on what, and where the edges are. Written to be read start to finish by someone who has not seen the code.

---

## What it's for

Two different questions, one design.

1. **"What is this customer allowed to do?"** — the licence subsystem.
2. **"Can this customer prove they stayed inside it, and that their records weren't doctored?"** — the compliance attestation.

The second is the hard one, because MATOFX runs air-gapped on hardware the customer controls with root access.

---

## 1. The three keys — everything depends on these

This is the root of the dependency tree. Get these wrong and nothing above them works.

| Key | Who holds it | What it signs | Why it exists |
|---|---|---|---|
| **Issuer key** | Funis only (hardware-backed at release) | The licence file, and the install-identity file | The root of trust. Its *public* half is baked into the MATOFX build at release time |
| **Report key** | Delivered to the customer *inside* the signed licence | Compliance reports | Proves a report came from the install Funis issued it to |
| *(install identity)* | Generated by the install itself at first boot | nothing — it is a name, not a key | Names the install a licence is issued **for**, so one licence cannot run two deployments |
| **Audit signing key** | Generated on the customer's own disk | Every audit record | Proves records weren't altered *since the install wrote them* |

The critical thing to understand: **the report key lives on the customer's machine.** A valid signature therefore proves "a holder of that key said this" — not "this is true". That single fact is why anchoring exists, and why §10 matters.

In the source tree the trusted-issuer map (`matofx/compliance/issuer.py`) is deliberately **empty**. Release engineering populates it when building an artefact. For dev and self-hosted verification, keys come from `[compliance].issuer_public_keys` in `matofx.toml`.

## 2. The licence file

A JSON file signed by Funis, stating: customer, `licence_id`, type, number of slots, issue and expiry dates, grace-period length, which features are on, optionally a machine binding, and the report key.

**Four gates on load, in this order** — the order matters, because each error message only makes sense once the previous gate has passed:

1. **Readable** — exists, is JSON
2. **Trusted** — the Funis signature verifies under a key this build trusts. *Everything after this point is asserting things Funis said, not things the customer's file claims.*
3. **Structurally valid** — required fields, known licence type, sane slot count and dates
4. **For this host** — if the manifest declares a machine binding, the observed fingerprint must match

A fifth check runs once the database is available (at licence install, at API startup, and on the runner's hourly tick): **is this licence for this install?**

**The install names itself.** At first boot MATOFX mints a random `install_id` in its own database; `matofx licence request` prints it; Funis issues a licence *for that id*. A second deployment mints a different id, so a copied licence is refused there.

That direction matters. Originally the id came *from* Funis inside the licence, which made it an identifier for the **licence** rather than the install — feed one licence to two deployments and both legitimately claimed it. Worse, an install that never ran `compliance adopt` had no identity at all and was exempt from binding entirely, which is exactly what a shadow instance would do. Binding to the install rather than the host is deliberate — `install_id` lives in the database, so it survives container rebuilds, VM moves and host migrations, which are exactly the events that break machine binding and force a reissue. Machine binding stays available as an issuer-chosen extra for hosts that never move.

What this does *not* stop is a clone of the whole database, which carries the `install_id` with it. Nothing local can — anything the install stores can be copied. That case stays detection-only (counter collision, §9), and a licence server on the customer's own network is the known upgrade if it ever becomes commercially material.

Any of the four failing → the process **refuses to start**. Someone edited the licence, or it belongs to another machine; that is not an availability problem, so degrading gracefully would be the wrong answer.

A *missing* file is treated differently — an administrative lapse, not tampering → **read-only**, not a refusal.

**Verification re-runs on every load**, never trusted from the database. The file on disk is the authority, and the hourly re-check exists precisely to notice it changing underfoot.

### The dev exemption

| Config | Result |
|---|---|
| `[licence].file` **not set at all** | Never licensed → **writable** (dev checkout, CI) |
| `[licence].file` set, file missing or expired | A genuine lapse → **read-only** |
| `environment = "prod"` with no `[licence].file` | **Refuses to load the config at all** |

Both halves are needed. Without the first, every developer checkout is read-only. Without the third, "just never configure it" runs unlicensed for ever.

> `environment` no longer controls whether the issuer signature is required — see
> **Gap 1** below for what changed and why.

## 3. The two licensing models

They meter genuinely different things, so the report carries a separate block for each and names which one is authoritative.

### CSL — Concurrent Session Licence

**N people signed in at once.** Slots churn minute to minute.

- **The gate sits at login** — after the password is verified (so a refusal never leaks whether an account exists) and before the session row is created.
- Admission is **two-phase**: a provisional decision, then a re-check once the session row exists. Counting and inserting are two separate steps, so a burst of simultaneous logins could otherwise all be told there is room. The re-check picks the loser by **rank** (position among live sessions by age), not by re-counting — otherwise five people racing for one place would all withdraw and leave it empty.
- **Slots free themselves**: sign-out, inactivity timeout, maximum session age, or an admin ending a session from *Active sessions*. This makes idle-logout load-bearing — without it, someone who walks away holds a place indefinitely.
- **Break-glass**: a Super User is admitted even at the cap. The alternative is an administrator locked out of their own site exactly when the licence needs fixing. It is recorded as its own event and broken out in the report, so a peak of 11 against 10 slots reads as *"1 break-glass admission"* rather than a breach.
- The binding figure is **peak concurrency** over the period.

### FAL — Floating Access Licence

**N named people who can sign in at all.** The number only moves when an administrator acts.

- A "floating assignment" is simply **a user account that can log in**. MATOFX has had that lifecycle since migration 0009; FAL puts a cap on it rather than adding a new concept.
- **The gate sits on activation** — creating an active user, or reactivating a deactivated one. At the cap you get a 409 and *the user is not created*.
- **Revoking is never gated.** An install must always be able to get back under its cap.
- Deactivated users keep their account, projects and settings; they just cannot sign in.
- The binding figure is **assignments held**.

### Both types

Read-only mode is **unmetered** for both. There is no metered work to protect when nothing can be submitted, and "every registered user may sign in and view results" cannot hold if the cap still turns people away.

## 4. Licence lifecycle

```
active  →  grace  →  expired
        ↑          ↑
   expires_at   + grace_period_days
```

- **active** — normal
- **grace** — expired but inside the grace window. Fully writable, with a banner counting down. A lapsed renewal must not take a customer offline.
- **expired** — past grace → **read-only**

Expiry is wall-clock. Moving the system clock forward a year produces grace or expired exactly as real time would.

### Features

The licence says which large features are on (parametric studies, optimisation, file library, …). Three deliberate rules so a licence problem never looks like a product fault:

- **Empty or absent feature list** → the config file's list applies. An absent list means *"this licence expresses no opinion"*, not *"nothing is licensed"*.
- **Present but all-false** → everything off. That distinction is intentional.
- **A feature this build doesn't have** → ignored and logged, never an error. A newer licence must keep working on an older install.

`matofx licence show` reports the **effective** set — what the site actually runs — and explains any divergence from the file.

## 5. Read-only mode — every trigger

Three things put a site into read-only, and they reach the middleware as one answer:

| Trigger | Lifted by |
|---|---|
| Licence missing, or expired past grace | Installing a valid licence |
| Audit-chain integrity check **failed** | Super User acknowledgement, with a written explanation |
| Integrity check **hasn't run for 24 hours** | Restarting the runner, or the same acknowledgement |

**What read-only actually means** — narrower than "block all writes":

- Every already-registered user may still sign in and view results
- No new registration, no access-rights or role changes, no submissions, no edits
- **Work already running finishes** — the runner is a separate process and deliberately is not gated
- A short allow-list keeps working: login, logout, session keep-alive, acknowledging the integrity failure, ending a session to free a place, and personal display preferences (theme, locale, timezone, sidebar)

The gate is one middleware over every mutating route, and it fails **closed** — a new route is blocked until someone deliberately exempts it. A test enumerates the app's real routes and fails if the exempt set changes, if an exemption goes dead, or if a mutating verb hides behind a `GET`.

One asymmetry worth knowing: if deciding *whether* the licence permits writes itself errors, that **fails closed** (read-only). If the integrity lookup errors, it fails open — a transient database blip should not 503 every write.

## 6. The audit chain

Underneath all of this sits a hash-chained, signed audit log that predates ADR-0019:

- Each record's hash covers its content **and the previous record's hash**
- Records are Ed25519-signed, and verification handles key rotations
- A singleton head row is locked on write, so the chain physically cannot fork
- `matofx audit verify` recomputes every hash and checks every signature

**What it proves:** nothing was altered since it was written.
**What it cannot prove:** that this is the *same* history you had last year. A customer with root can rebuild the entire chain from scratch and it will self-verify perfectly.

That gap is the whole reason the compliance report exists.

---

## 7. The Merkle tree — the part that closes the gap

On top of the same record hashes, MATOFX builds a **Merkle tree** (RFC 6962 — the Certificate Transparency standard, so third-party tooling can check it).

The useful property is a **consistency proof**: small evidence that today's log is an *append-only extension* of a log you saw before. One primitive answers three questions at once:

- Records **removed** → no proof can exist
- Records **altered** → the proof fails to reconstruct the old root
- Records merely **added** → the proof verifies

It is small and stays small. In the worked example a **343-record extension is proved in 7 hashes**; a 90,000-record chain needs about 17. This is why annual reporting works — shipping the actual record hashes for a year would be megabytes.

**Each report carries a proof from every report the install has ever generated.** That sounds redundant but is the load-bearing detail: the install cannot know which of its reports Funis actually received, so it proves from all of them and lets Funis pick the one they hold. This is what makes a report you generated and never sent completely harmless.

## 8. The compliance report

Generated on demand — `matofx compliance report` — and **pull-based**. Nothing is transmitted by the app; there is no phone-home. Expected cadence: **once or twice a year**.

**What is in it:**

- Install and licence identity, and whether the install could verify its own identity against a trusted Funis key
- The full-range self-verification result, including failing record ids verbatim
- The Merkle root and the consistency proofs
- A monotonic report counter
- When the install last verified itself outside this report
- Counts of licence events (installs, validation pass/fail, slot grants and denials, break-glass, assignment changes, expiry transitions)
- Individually-listed serious events, capped at 100
- Usage figures — peak concurrency vs slots, assignments vs slots

**What is not in it:** no project names, job names, file names, or usernames. Actors appear as opaque ids (`user:1`), so it is **pseudonymous rather than anonymous**. This matters commercially — customers resist shipping raw audit records, and a refused report is worth nothing.

Every report is archived in the database so a re-request is answerable, and ships with a readable HTML twin containing no external assets.

**It never fails closed.** A broken chain, a missing licence, or a breach must still produce an artefact *saying so*. Refusing to emit at exactly the moment something looks wrong would destroy the evidence needed to explain it.

## 9. Verification at Funis — three verdicts

`matofx compliance verify <file> --ledger <file>` runs six checks and returns one of three verdicts.

| Verdict | Meaning |
|---|---|
| `CONSISTENT` | Everything checks out |
| `INCONCLUSIVE` | Something could not be checked — no ledger entry yet, a baseline that attested no records, a missing proof |
| `CONTRADICTED` | Something **failed** — a proof that does not verify, a counter that went backwards, a bad signature |

**The asymmetry is deliberate and is the most important design point in the whole ADR.** Anything unverifiable lands in `INCONCLUSIVE`; only a positive failure contradicts.

The reason: a false accusation is worse than a missed one. If the vendor cannot tell a fraud from a customer who previewed a report, the verdict cannot be acted on *at all* — false positives destroy the evidential weight of the true ones. This is exactly the defect the 2026-08-11 rework fixed, where any install that generated a report without sending it was permanently and unrecoverably marked as fraudulent.

Two signals worth reading carefully:

- **A counter gap** (`5 skips 3..4`) is a **warning**, not a finding. Reports are generated on request, so this usually means one was produced and not sent.
- **A counter going backwards** is a contradiction with three possible causes: the same report sent twice, a database restored from an older backup, or **two installs running from the same identity** — a clone. The clone is the one to rule out first, because it is the only one that is not an accident.

### The ledger's own integrity

Every verdict above is measured against the ledger, so the ledger needs protecting too — and until 2026-08-12 nothing protected it. It is now **chained and signed**: each entry carries the hash of the one before it, is Ed25519-signed with a Funis ledger key, and a signed `.jsonl.head` sidecar records how many entries there should be.

The sidecar is not redundant. A hash chain catches an entry that was edited, reordered or removed from the *middle*, because every later `prev_hash` stops matching — but it cannot see a ledger **cut short at the end**, since what remains is a perfectly valid chain one entry shorter. That is simultaneously the most likely accident (a partial copy, a truncated write, a restore from an older snapshot) and the most useful deliberate edit. Only a recorded length catches it.

Two deliberate softnesses: unsigned entries written before this existed stay **readable** and verify as `unsigned` rather than failing, because refusing to read them would destroy the history being protected; and a missing sidecar warns rather than accuses. The one thing refused outright is a **downgrade** — once a ledger holds signed entries, an unsigned append is rejected, or signing could be bypassed by simply not passing a key.

**Its honest limit**, in the same register as everything else here: whoever holds the ledger key can re-sign a rewritten ledger. Keeping that key off the machine that stores the file is an operational control, not a cryptographic one. What signing closes is *silent* corruption, and it is what lets the ledger stand up to someone who does not simply take Funis's word for it.

## 10. What runs when

| When | What |
|---|---|
| **Config load** | Prod refuses to start without a licence configured |
| **Startup** | Full licence verification (fail-closed on tampering); incremental integrity check on the chain's tail |
| **Every hour** | Licence re-check + full audit-chain walk, in the runner |
| **Every login** | CSL slot check (two-phase) |
| **Every admin activation** | FAL assignment check |
| **Every mutating request** | Read-only gate |
| **On demand** | Compliance report; `matofx audit verify` |

**Both the API and the runner attest**, so neither is a single point of failure. That was a real hole until the rework: the hourly walk lived only in the runner, so an install running without one never checked its chain at all.

And attestations **expire**. A recorded verdict says "the chain was intact *when it was checked*", so it cannot stand for ever — an install whose checker died would otherwise keep serving on an arbitrarily old verdict with nothing to say so. Banner at 3 hours, read-only at 24. Same pattern as a certificate's expiry date: the absence of checking becomes self-enforcing rather than something a separate watchdog must notice.

## 11. Operational duties this creates

**On the Funis side — not optional:**

- **Retain the ledger for every install.** One line per report received: counter, tree size, root. Lose it and that install's history becomes unprovable, permanently.
- **Record every report you receive.** The ledger's newest entry is what future proofs are checked against. A report you verify but forget to append is a report that does not protect you.
- Keep issuer keys hardware-backed, and populate the trusted map at build time.
- **Run `scripts/ledger.py backup` on a schedule.** It verifies before copying and refuses a ledger that fails, so the day it starts failing is the day you still have an intact copy. Back the issuing registry up in the same job — the ledger proves what was received, the registry says who it was issued to.
- **Pass `--public-key` when verifying an install's first report.** Otherwise no report key is ever pinned and every later report *skips* its signature check instead of running it.

The full procedure — issuing, receiving, backups, key rotation, and how to read
each verdict — is in [`funis-vendor-runbook.md`](funis-vendor-runbook.md).

**On the customer side:**

- Keep the runner running, or the site goes read-only after a day
- Generate reports when asked; generating extra ones costs nothing

## 12. The honest limits

State these plainly in any security review. Overstating them is the one way this design fails one.

- **It is tamper-evident and rollback-detectable. It is not tamper-proof.** A licensee who extracts the issued report key, rebuilds the chain, *and* keeps every proof consistent across every future report defeats it.
- **The evidential weight is in the ledger Funis keeps**, not in the signature.
- **Clone detection needs both copies to report.** It works by counter collision — both forks issue report N, and the second to arrive is caught. If only the clone ever reports, it is indistinguishable from the original going quiet. That gap cannot be closed in software on hardware the customer controls.
- **Never say "tamper-proof" in sales material.**

### The frame that makes this commercially sound

Enforcement is **contractual**; the software supplies evidence. This is how IBM's ILMT and Oracle LMS work — the vendor does not cryptographically prevent under-reporting; it *requires* the tool to be run and the reports retained, and a customer who cannot produce consistent evidence defaults to the worst-case licence position.

That framing changes what the software has to be good at. Not catching a determined attacker — impossible here. Instead: making inconsistency **impossible to avoid without deliberate, sustained, provable lying**, while never accusing an honest customer.

Two upgrades would genuinely raise the ceiling; neither is needed for the first client:

- **RFC 3161 trusted timestamps** applied at Funis on receipt — closes backdating, legally recognised under eIDAS
- **TPM-backed monotonic counters** where the platform offers one

Gaps 1–4 are closed. The **"ready to issue a real licence" milestone (gaps 2, 3
and 4) is complete**: a licence can be issued and installed, and the vendor-side
ledger it is checked against now has tooling, integrity protection and a written
process ([`funis-vendor-runbook.md`](funis-vendor-runbook.md)).

> day's own work. Four defects found and fixed: a licence issued for
> *another install* was honoured on a running server (the request path
> never checked binding); the live-features cache keyed on `(mtime, size)`
> and so could miss a real licence change; deleting the ledger's head
> marker hid a truncation; and a licence alert could stall a sign-in by
> 30s per administrator when the mail relay was unreachable.

**Gaps 1–11 are all closed as of 2026-08-12.** This section is kept as the
record of what was wrong and why each answer was chosen — several of the
decisions (break-glass unlimited by design, `INCONCLUSIVE` over accusation)
