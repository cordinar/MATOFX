# Contributing to MATOFX

Welcome. This file is the contract between everyone who touches the MATOFX v2 codebase — currently the maintainer plus AI collaborators, and any future contributors.

> **Read first:** `PROJECT_BRIEF.md` is the source of truth for **design decisions**. `ROADMAP.md` is the source of truth for **delivery progress**. If the answer to "why does this work this way?" isn't obvious from the code, it should be in one of those two — or in an ADR (see below).

---

## Ground rules

1. **The legacy v1 application is reference only.** It is not part of this repository; `ARCHITECTURE.md` §1-15 summarises its design for anyone porting a concept across.
2. **Permissively licensed dependencies only.** No SSPL, RSAL, BUSL, or AGPL. BSD / MIT / Apache-2 / PSF / MPL are fine. Use Valkey, not Redis. If unsure, check with the maintainer before adding the dep.
3. **Performance and security are equally weighted.** Never trade one for the other; surface the conflict and engineer a third path.
4. **MATOFX does the heavy lifting.** Tool authors write tiny orchestrators (tens to low-hundreds of lines). The framework owns forms, validation, staging, sandboxing, audit, licensing, retries, notifications. If a change pushes complexity onto tool authors, push back.
5. **No Dockerfiles in tool bundles.** Descriptors declare high-level runtime needs; MATOFX synthesises images from a curated base-image library. The word "Docker" should never appear in tool-author-facing surfaces.
6. **End-users are not modellers.** Every user-facing surface is plain English, jargon-free, sensibly defaulted, with per-field error messages and inline help. The test is "would a non-expert understand?"
7. **Every feature is Funis-toggleable per customer.** Non-essential features go in `features.toml`, gated by `feature_enabled("name")`, controlled via the signed licence manifest at ship time.
8. **UI stays close to the legacy MATOFX UI for now.** Before designing a new screen, read the equivalent legacy screen described in `ARCHITECTURE.md` §1-15 and use it as the starting point. Page names, navigation order, primary action labels, and overall layout should match the legacy — a user who used the legacy app must immediately know where things are. Improvements to copy / errors / accessibility are welcome; visual or structural reinventions are deferred until after the pilot. The "intuitive and simple to use" bar applies to every surface.
9. **Legal name is Funis Consulting Ltd.** Use the full name in copyright notices, licence headers, package metadata, customer-facing docs, and signed manifests. Casual prose can use "Funis". Never "Funis Software" or any other variant.

## Branching and review

Trunk-based with a lazy long-lived maintenance branch (per §H41 of the brief).

- `main` is the default branch and the release line.
- Work happens on short-lived topic branches (`topic/<short-name>`), opened off `main`, merged back via PR.
- Commits land in `main` only via PR. Direct pushes are reserved for documentation typos and similar trivia, and even then prefer a PR.
- A `release/x.y` maintenance branch is cut **lazily**, only when a customer needs a backport that can't go to `main`. Do not preemptively create release branches.
- **PRs are small.** Review is the rate-limiter for a solo + AI build; one screen of diff is the right unit, two screens is the upper bound, anything larger is a smell. Split the work.

### PR template

```
## What
One sentence: what this PR changes.

## Why
One paragraph: motivation. Link the brief section / ADR / roadmap row.

## How tested
Bullet list. New tests, manual checks, screenshots if UI.

## Risk
Anything to watch in production. "None" is a valid answer for low-risk PRs.
```

### AI-assisted contributions

Code generated by an AI tool follows the same rules as human-written code: review before merge, lint-clean, test-covered, conforms to the architecture in the brief. The fact that a diff was machine-generated is not an excuse for skipping review or testing — if anything, it raises the bar.

## Local development

### Prerequisites

- Python 3.12 or 3.13.
- Postgres 16+ (only needed for the Postgres test job; SQLite-only dev works without it).
- Valkey 7+ (only needed for queue-backed paths once Phase 1 begins).
- A POSIX shell or PowerShell. Both Windows and Linux are first-class targets — if a script is shell-specific, provide both forms.

### Setup

From ``:

```bash
python -m venv .venv
. .venv/bin/activate          # Windows: .\.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
```

### Quality gates (run these before pushing)

```bash
ruff format --check .
ruff check .
mypy
pytest
```

The CI matrix (`.github/workflows/ci.yml`) runs the same commands on Linux + Windows × SQLite + Postgres. Local pre-flight should mirror CI.

### Running a single test

```bash
pytest tests/path/to/test_thing.py::test_specific_case -v
```

### Postgres tests

```bash
export MATOFX_TEST_POSTGRES_URL=postgres://matofx:matofx@localhost:5432/matofx_test
pytest -m postgres
```

Tests not marked `postgres` run against an ephemeral SQLite file.

### Hashed lockfile (`requirements.lock`)

Production installs use a hashed lockfile so an artefact swap on PyPI can't slip a different wheel into the build. Day-to-day dev install (`pip install -e ".[dev]"`) does **not** use the lockfile — the resolver picks live versions, the lockfile pins them.

Regenerate the lockfile from a Linux runner whenever `pyproject.toml` changes:

1. Maintainer triggers the **Regenerate lockfile** workflow (`.github/workflows/lockfile.yml`) via the GitHub UI's *Run workflow* button on the `main` branch. Optional reason text shows up in the PR body.
2. The workflow runs `pip-compile pyproject.toml --extra postgres --extra dev --extra supply-chain --generate-hashes` on Ubuntu / Python 3.12 and opens a PR if the file changed.
3. Review the diff, confirm the CI **Verify hashed lockfile installs cleanly** job passes, and merge.

The lockfile is platform-specific (linux/x86_64, py3.12). If MATOFX ever ships Windows / macOS wheels we'll need a per-target lockfile; not on the v1.0 list.

Local-only regeneration (when you're iterating before opening the workflow PR):

```bash
pip install -e ".[supply-chain]"
pip-compile pyproject.toml \
  --extra postgres --extra dev --extra supply-chain \
  --generate-hashes \
  --output-file requirements.lock
```

Run this on Linux — the resolved set differs from Windows in subtle ways (manylinux wheel availability, native deps).

## Architectural decisions (ADRs)

Decisions captured in `PROJECT_BRIEF.md` are the foundation. Anything **architectural** that goes beyond the brief — a new dependency, a new public interface, a new module boundary, a behaviour change with downstream implications — gets a short ADR.

- File: `decisions/<NNNN>-short-name.md`. Numbering is monotonic.
- Template:

  ```markdown
  # NNNN. Short decision title

  Date: YYYY-MM-DD
  Status: Proposed / Accepted / Superseded by NNNN

  ## Context
  Why is this decision needed? What's the situation?

  ## Decision
  What did we choose, and why this option vs the alternatives.

  ## Consequences
  What changes as a result. Anything to revisit later.
  ```

- ADRs are append-only. Superseded ones stay, with a Status pointer to the replacement.
- ADRs that affect the brief **also** update the brief — the brief stays the source of truth; the ADR explains *why* a decision changed.
- Trivial daily choices (variable names, helper structure) belong in commit messages, not ADRs.

## Coding conventions

- **Type hints everywhere.** `mypy --strict` is the bar; `Any` requires justification.
- **Docstrings on public functions, classes, and modules.** Google style. Internal helpers can omit them; intent should be clear from name and signature.
- **No comments that explain `what`** — well-named identifiers do that. Comments are for `why`: hidden constraints, subtle invariants, workarounds for specific bugs.
- **Errors are user-facing copy.** Per §F30 / the "users are not modellers" rule, error messages exposed to end-users are plain English, with the *what* and *what to do next*. Internal exceptions can be terse, but anything that reaches a UI surface goes through the user-facing-message layer.
- **No globals, no module-level state.** Configuration is passed in. Tests must be able to run in parallel.
- **Pathlib over `os.path`.** `pathlib.Path` everywhere; `os.path` only when interfacing with a library that demands strings.
- **f-strings or `.format()`, never `%`-formatting.**

### Per-customer feature flags

Every non-essential feature is gated by `feature_enabled(settings.features, Feature.X)` so Funis can ship the same artefact to every customer and toggle features at install time via the signed licence manifest.

- The catalog of feature slugs is **closed** — `matofx.features.Feature` (a `StrEnum`). Adding a feature requires a code change.
- Customers enable features at install time: in production via the signed licence manifest, in dev via the `[features].enabled` list in `matofx.toml`.
- Unknown feature slugs in configuration are rejected at validation time, the same way unknown permissions are.

When you ship a new toggleable feature:

1. Add a member to `Feature` in `src/matofx/features.py`. One-line docstring on the member describing what it gates.
2. Wrap the gate point: `if feature_enabled(settings.features, Feature.X): ...`.
3. Mention the new slug in `etc/matofx.example.toml` (commented under `[features].enabled`).
4. Decide whether the pilot customer should have it enabled; if so, add it to their licence manifest.

Essential / core features — auth, hierarchy, the audit log — are not gated. Only customer-toggleable features go in the catalog.

### Hardcoded values — strict rule

Customer-tunable behaviour **never** has a default outside `matofx.config`. The Pydantic field defaults in `Settings` and its sections are the single source of fallback values; nothing else in the codebase is allowed to introduce a second layer.

Concretely, every literal in source code must fall into exactly one of these three categories:

1. **A Pydantic field default in `matofx.config.models`.** The customer can override it via `matofx.toml` or `MATOFX__*` env var. Sensible fallbacks live here and nowhere else.
2. **An identity / convention constant.** Internal handler names (`"matofx.obs"`), env-var prefix (`"MATOFX__"`), file-naming convention (`"matofx.toml"`), stdlib field-name sets — the customer cannot meaningfully change these without breaking the deployment contract. Keep them at module level next to where they're used.
3. **An I/O contract default.** Function-signature defaults like `stream: IO[str] | None = None` resolving to `sys.stderr`, `argv: list[str] | None = None` resolving to `sys.argv[1:]`, `path: Path | None = None` resolving to a documented lookup chain. These are documented function contracts, not behaviour configuration.

What is **not** allowed:

- A function-signature default that mirrors a Pydantic default. E.g. `def configure(level: str = "INFO")` while `LogSettings.level = "INFO"` already exists. That gives the codebase two sources of truth that can silently diverge.
- A magic number embedded in business logic that the customer might reasonably want to tune (timeouts, batch sizes, retry counts, polling intervals, pool sizes). Add a field to `Settings` and read it.
- An environment-specific guess (e.g. defaulting `environment = "dev"`). Critical fields stay required and the loader fails loudly when they're missing.

The litmus test: **could a customer reasonably want to change this value at install time?** If yes, it belongs in `Settings`. If no, it's a code constant — and it stays in code.

## Project structure

```
.
├── PROJECT_BRIEF.md          # design decisions (locked)
├── ROADMAP.md                # delivery progress (living)
├── ARCHITECTURE.md           # §1-15 legacy reference; §16+ as-built record
├── INSTALL.md                # build the bundle, install on a target machine
├── MIGRATE_GUIDE.md          # move tools / workflows between installs
├── CONTRIBUTING.md           # this file
├── decisions/                # ADRs
├── designs/                  # per-feature design documents
├── etc/                      # matofx.example.toml + example branding
├── branding/                 # default header / footer / favicon assets
├── example_tools/            # reference tool bundles a fresh install can seed
├── example_materials/        # starter material catalogue (seed.json)
├── scripts/                  # install, start/stop, bundle build, seed helpers
├── pyproject.toml
├── alembic.ini
├── src/matofx/
│   ├── audit/                # hash-chained signed audit log
│   ├── cli/                  # admin CLI (`matofx ...`)
│   ├── config/               # config loader (file + env)
│   ├── db/                   # SQLite + Postgres data layer
│   ├── docs/                 # single-source help (public / user / admin)
│   └── obs/                  # JSON-Lines logs, Prometheus, OTel
├── tests/
└── .github/workflows/
```

Each `src/matofx/<package>/` has a `README.md` describing purpose, key types, and where to start reading.

## Documentation expectations

Per §I47 of the brief, all four customer-facing docs ship with v1.0:

- **Install guide** — air-gapped install on Linux + Windows + cloud VM.
- **Admin guide** — day-2 operations.
- **Tool-author guide** — `*_descriptors.json`, the SDK, base-image catalogue, examples.
- **End-user guide** — short, friendly, plain-English.

These live in `src/matofx/docs/{public,user,admin}/` as single-source Markdown (ADR-0014): the same files feed the in-app `/ui/help` browser and the standalone HTML/PDF build. **A feature change updates its chapter in the same commit.**

## When in doubt

- Ask the maintainer.
- Write it down — in the brief, in an ADR, in the commit message, in the PR description, in the per-module README. The institutional memory of this project is the trail of writing.
